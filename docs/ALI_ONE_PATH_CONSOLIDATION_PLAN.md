## The mandate (verbatim, owner's own words — this is the standard everything below is judged against)

> "i dont want multiple paths.. that fast path was a debugging addition to just see if the model could program. it can be deleted without any tears... i want one path, i want her truthful, reliable, and fast... thats the requirement. if the systems help then keep them, if they add bloat and do not help those requirements then remove them. this is a personal assistant not a fortune 500 company assistant that will be on everyones desktop... it needs to work for me essentially, its not going to run on the supercomputers at ibm... i need it reasonable to run on my computer.. 14700k, 32GB Ram, 5070Ti... if it can't do that then its a failure, if a system is way overboard for what i need then remove it, if it helps what I am needing then keep it,.,, for the entire program from when i click the send button to the time it returns on my screen and finishes its work tht is your domain... and yes please enable streaming"

Every decision in this plan is judged against exactly three things, for exactly one hardware target (single-user desktop, 14700k / 32GB RAM / 5070Ti, not enterprise scale):
1. **Truthful** — never claims something happened when it didn't.
2. **Reliable** — always completes, or fails honestly, not silently or stuck.
3. **Fast** — send-to-response latency, the whole path, is this session's domain end to end.

Anything that doesn't serve one of those three, for this one machine, gets cut. Nothing gets kept out of sunk-cost or "might need it later."

### Just confirmed by direct code trace (Explore agent, full report kept in session — key facts below)

- **The heavy orchestrator (`AliOrchestrationPlanningClient`, decisionJson protocol) is already unreachable from the live UI.** Every real user turn goes through `AliMinimumMessage`/`RunCoreAssistantAsync` only (`AliToolCoordinator.ProduceAgentTurnAsync` unconditionally calls the fast path). The heavy path's only entry points (`AliAgentHarnessRunner.ResumeAsync`, `ResolveRecoveryAsync`) have no live caller — `ResumeAsync` has zero callers anywhere in `src/`, and the UI method that would reach `ResolveRecoveryAsync` (`MainWindowViewModel.ResolveRecoveryDecisionAsync`) is already stubbed out with a comment saying recovery decisions aren't part of the active path.
- **This means "one path" is already true in practice.** What remains is not a merge/routing fix — it's (a) deleting the now-pointless dead code so it stops being confusing bloat, and (b) deciding, tool-by-tool, which of the heavy path's durability properties are worth re-adding *to the one real path* versus leaving cut.
- **Real reliability gap found:** the live fast path (`AliMinimumMessage.RunAsync`) has **no completion verification at all** — it trusts the model's own text as-is, with only a 64-tool-call hard cap as a backstop. A real, already-written, mechanical (non-LLM, cheap) checker exists — `CoreAssistantCompletionGate` — that verifies build/run/mutation success without needing the heavy protocol, but it's currently compiled out behind `#if false` (`AliAgentHarnessRunner.cs:1217-1607`). This is the single highest-value "reliable" fix identified so far, and it does not require reviving anything heavy.
- **Persona is already correct on the fast path** — the heavy path actually strips persona/identity for every model call it makes (`SuppressInjectedPersona = true`); the fast path already correctly injects it. No fix needed here, fast path is already better.
- **Durability primitives, reusability verdict (for Phase 3 decisions later):**
  - `EvidenceLedger` — genuinely standalone, cheap, already proven reusable outside the coordinator (`AliFrameworkFileMutationTransaction` uses it directly). Safe to keep/reuse.
  - `AliSourceChangeSetStore` (changesets/rollback) — architecturally standalone, but the fast path currently bypasses it entirely with raw disk writes (`AliCoreAssistantExecutionContext.IsActive` branch in `AliFrameworkFileMutationTransaction.PublishFrameworkWriteAsync`). Candidate for wiring in if the latency cost is acceptable — not yet measured.
  - `AliExecutionBroker`/`AliExecutionGrant` (execution grants) — **resolved, provably dead-in-practice (logical proof, not just a strong signal).** It's referenced outside the dead orchestrator (by the Roslyn code-action files), but every one of its real call sites (`AliCodingModule.cs` lines 558-628, `AliRoslynCodingTools.cs`, `AliDotNetProjectScaffolder.cs`) is gated by `AliCoreAssistantExecutionContext.IsActive ? <direct/simple branch> : <grant-consuming branch>`. Combine two already-confirmed facts: (1) `RunCoreAssistantAsync` — the only live conversational path — unconditionally calls `AliCoreAssistantExecutionContext.Enter()`, so `IsActive` is always `true` on every real turn; (2) the only code path that could ever run with `IsActive == false` is the heavy orchestrator (`AliOrchestrationPlanningClient`'s `RunCoreAsync`), which was already proven to have zero live callers anywhere in the app. There is no third path. Therefore the grant-consuming branch of every one of these coding tools is unreachable in the running app, full stop — not a probability, a proof from facts already on record above. Still a candidate for a separately-reviewed deletion pass (it's real, working, well-built infrastructure — deleting it is a decision worth a deliberate look, not a snap judgment), but the safety question itself is now closed.
  - `TurnTransitionWriter` (turn journal) — publicly reachable but shaped entirely around the decisionJson protocol's own vocabulary (prepare/commit/resolve). Not a generic logger. Not cheaply reusable as-is.
  - `AliCompletionCritic` (LLM-based critic) — never instantiated anywhere today, fully dead, requires a fully-formed durable turn to exist at all. This is very likely a straight CUT, not a re-enable — `CoreAssistantCompletionGate`'s mechanical checks look like the right-sized replacement for a consumer desktop, not an LLM-judged critic pass on top of every turn.

### Phase 1 — Real streaming, send-to-screen
**Status: DONE — verified empirically against a real backend, not just code review.** Built a temporary integration test that called the real, unmodified `OpenAiCompatibleLocalModelRuntime.GetStreamingResponseAsync` (the exact production method) against the owner's actual running LM Studio server (127.0.0.1:1234, qwen2.5-coder-14b) and logged every chunk with a timestamp. Result: **50 real text chunks arrived incrementally over an 803ms span** (first at 282ms, last at 1090ms), forming the correct answer — not one buffered block. Along the way this also surfaced a minor, separate hardening opportunity worth a future look: LM Studio returns its own error bodies with HTTP 200 instead of a 4xx/5xx, and the SSE parser correctly no-ops on that non-SSE line rather than crash, but that means a genuinely malformed/misrouted request currently fails silently (empty answer) instead of surfacing a clear error — not urgent, not a regression, just noted. The temporary test file and temporary diagnostic logging were both removed after use; nothing was left behind. What remains unverified is purely the WPF rendering layer (does the on-screen TextBox visually update per keystroke) — the actual data-arrival mechanism is now proven end-to-end against a real backend, not simulated or assumed.

### Phase 2 — Delete the dead heavy path
**Status: NOT STARTED.**
**Scope:** Remove `AliOrchestrationPlanningClient`, `AliAgentHarnessRunner.ResumeAsync`, `ResolveRecoveryAsync`, `RunCoreAsync`, the `#if false` `RunDisabledLegacyCoreAssistantAsync` block, `AliCompletionCritic`, and the `AliCompletionComposer` heavy-path composition call, **once and only once each is confirmed to have no other live dependent.**
**Why this order:** deleting confirmed-dead code is low-risk and directly answers "delete the fast-path-only framing, one path only" — but must not be done blind. Some of these types (`EvidenceLedger`, parts of `TurnTransitionWriter`) may be referenced by things outside the dead call chain (e.g. the changeset system, or file-mutation transactions) that need to survive. Each deletion candidate needs its own "what else references this" check before removal — no bulk deletion.
**Not yet done:** the dependency check itself.

### Phase 3 — Close the real reliability gap
**Status: DONE (code-verified), live-app testing still owed.**
**What shipped:** `CoreAssistantCompletionGate` is now instantiated in `AliMinimumMessage.RunAsync` and fed via `Track`/`Observe` on every tool call/result. Before accepting the model's final text as done, `TryGetBlocker` is checked. If it finds a real problem (a tool call with no terminal result, a failed create/build/test/run/stop, or — the main win — source edited but not followed by a fresh successful build of that exact revision), the answer is NOT published; instead the blocker's own continuation instruction is fed back to the model as a forced next turn (visible to the user as a live self-correction, since streaming already shows text as it's generated — there's no way to "unshow" a premature claim once it's streamed, so this turns a silent lie into a visible correction instead). Bounded to 3 retries; if the model still won't produce a verified answer, the gate's own pre-written truthful failure text is published instead of trusting the model further.
**Deliberately NOT wired in:**
- The original upfront LLM classifier (`ClassifyCoreCodingRequirementsAsync`) that this gate was paired with in the old disabled code. It adds one extra model round-trip to *every single message*, including plain chat — directly against the "fast" mandate for a feature that mostly matters for coding turns. Skipping it means the gate's classifier-gated blockers (`workspace-work-not-started`, `workspace-mutation-not-started`, `required-build-missing`, `required-run-missing`) never fire — only the unconditional, mechanically-triggered blockers do. This is an intentional scope cut, not an oversight.
- The gate's unconditional `run-missing-or-stale` blocker, which as written demands a fresh successful run after *any* source edit regardless of whether the user asked for one — risked forcing pointless/inapplicable run attempts (e.g. editing a class library with no runnable entry point) and burning the tool-call budget. Explicitly filtered out in `AliMinimumMessage.cs` (`SkippedBlockerCode`). A model that chooses to run on its own initiative and hits a failure is still blocked by the (not skipped) `run-failed` check.
**Build:** verified clean, 0 warnings/0 errors. **Not yet verified:** actual live behavior in the running app — need to watch a real "claims success but build actually failed" scenario get caught and self-corrected, and confirm ordinary chat shows zero added latency (should be, by construction — Track/Observe/TryGetBlocker are all in-memory with no I/O when no coding tools were called this turn).

**Empirically verified end-to-end, not just unit-tested.** Built a temporary integration test (same pattern as the existing `AgentHarnessFinishReasonIntegrationTests`, deleted after use) that ran the real, unmodified `AliAgentHarnessRunner` → `RunCoreAssistantAsync` → `AliMinimumMessage` pipeline with a scripted model against **real file I/O**: pre-created a real file on disk, had the scripted model genuinely attempt to write to it (real `McpSourceFileTools` call, real failure — "file already exists"), then had the model falsely claim "I've saved the file successfully!" anyway. Result: **the false claim was never published.** Ali made 5 real model round-trips rejecting the lie before publishing the truthful answer ("I could not complete the latest requested source change. The file already exists...") — and the file on disk was verified never actually overwritten. This is the exact failure mode "never lie about whether a file was saved" exists to prevent, proven with a real failure, not a mock.

**Real bug found and fixed while building that test — a genuine gap in this session's own Phase 3 work.** Designing the test surfaced that `AliMinimumMessage` deliberately never calls `gate.Require(...)` (to skip the classifier round-trip), and the gate's failed-mutation blocker was gated behind that exact requirement flag — meaning **a failed file write/replace/delete produced zero blocker on the live path**, unlike build/run/test/create/stop failures, which were already unconditional. Fixed in `CoreAssistantCompletionGate.cs`: promoted the mutation-failure check to unconditional, consistent with every other terminal-failure check. The integration test above was run against this fix and is direct proof it now works correctly for real.

**Bonus fix found along the way:** running the gate's own pre-existing unit tests (`tests/Ali.Framework.Tests/CoreAssistantCompletionGateTests.cs`) surfaced a real, pre-existing bug independent of my wiring: the gate never re-required a launch after the app was explicitly stopped (`dotnet_stop_project`) unless source was *also* edited — so Ali could have claimed "it's running" right after stopping it. Fixed in `CoreAssistantCompletionGate.cs` by adding a dedicated `_runInvalidated` flag and a new `run-stopped` blocker code, kept deliberately separate from the "forced run after every edit" `run-missing-or-stale` code so `AliMinimumMessage`'s existing filter doesn't also swallow this legitimate truthfulness check. Also fixed 4 of the gate's own tests that were failing for unrelated, pre-existing reasons (unrealistic mock tool-call arguments/results that didn't reflect real tool payloads) — all 9 gate tests now pass.

**Full regression sweep run:** `dotnet test` across the whole `Ali.Framework.Tests` suite (1751 tests) shows 51 pre-existing failures, none caused by this session's changes — verified by (a) empirically reverting the gate wiring and confirming the one plausibly-related failure (`AgentHarnessFinishReasonIntegrationTests`) fails identically either way, and (b) tracing the other suspicious failures (`SemanticToolCatalogTests.CoreAssistant_*`) to `AliAgentHarnessRunner.ResolveCoreToolNames`, a method with zero callers anywhere in `src/` — dead code, unrelated to the live `RunCoreAssistantAsync` path, and already mismatched with its own `CoreRecoveryToolNames` constant before this session touched anything. The remaining ~45 failures are environment-dependent (missing git/gcc/Arduino CLI/LM Studio/Gemini API access in this sandbox), not code defects. Full breakdown not itemized further here to save space — rerun `dotnet test tests/Ali.Framework.Tests/Ali.Framework.Tests.csproj -c Release` if this needs re-verification.
